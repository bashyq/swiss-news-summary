Trip Planner — Design Overview

Review each section. Let me know if anything feels off.

1. Entry Points

Primary
Calendar Detection
App spots calendar events with locations outside your home city. Shows nudge card on Plan tab.
Secondary
Sunshine / Snow CTA
Existing "Plan a day here" buttons on destination cards. Pre-fills destination + date, goes straight to plan.
Workaround
Add Calendar Event
For spontaneous trips (Grindelwald invite), user adds a calendar event with location → detection picks it up.

2. Detection Logic

// On Plan tab load / date change
Scan calendar events for selected date
→ Filter to events with a structuredLocation
→ Reverse-geocode each location → get locality name
→ Compare locality to home city (e.g. "Zürich")
→ If different → this is an away event
→ Show nudge card with event title, location, free time windows

3. The Flow (tap "Plan my day in Meggen")

Step 1
MKLocalSearch
Fetch POIs near destination: restaurants, cafés, playgrounds, parks, museums, bakeries, lakes
→
Step 2
Weather
Open-Meteo for destination lat/lon. Already client-side capable.
→
Step 3
Gap Analysis
Calendar event = anchor. GapAnalysisEngine finds free windows (already city-agnostic).
→
Step 4
AgendaComposer
Claude picks best POIs for family day. Weather-aware, time-aware. Same API call as today.
→
Step 5
Deal Cards
Same PlanSlotCard UI. Lock, unlock, remove, replace — all works as-is.

4. What Changes vs Current Plan Tab

Component Current (7 cities) Trip (any destination)

Restaurant data Worker /lunch endpoint MKLocalSearch (restaurants)
Weather Open-Meteo (client-side) Same — any lat/lon
Gap analysis GapAnalysisEngine Same — city-agnostic

Persistence PlanStore (city-date key) Same — locality name as key
UI cards PlanSlotCard Same
Hero banner "Plan your Monday" "Your day in Meggen"

5. New Components

TripDetector
Service that scans calendar events, geocodes locations, compares to home city. Returns detected away-events for a date range.
POISearchService
Wraps MKLocalSearch. Parallel queries for multiple categories, deduplicates, returns unified POI pool for AgendaComposer.
TripNudgeCard
SwiftUI view on Plan tab when away-event detected. Navy card with event details, free time windows, "Plan my day in [place]" CTA.
AgendaComposer changes
Accept MKLocalSearch POI pool alongside curated activities. Format POI data for Claude prompt. Minor prompt update.

6. What We're NOT Building

✗ Manual destination search UI (calendar is the entry point)
✗ Multi-day trip planning (one day at a time)
✗ Hotel/accommodation search
✗ Transit routing to the destination (just planning once there)
✗ Photo fetching for arbitrary POIs (gradient + icon fallback)
✗ New backend endpoints (all client-side: MKLocalSearch + Open-Meteo)
